## Session 3 — Render build failure triage (commits c86cd54, 92914f0)

The Render deploy of the merge failed. Triaged against GitHub Actions (same
steps) and reproduced locally. Three findings, all fixed:

### 1. Root cause of the Render/CI failure: frontend lock out of sync

The morning's hardening commit added eslint devDependencies to
`frontend/package.json` but never regenerated `frontend/package-lock.json`
(unchanged since the initial commit), so `npm ci` hard-failed with EUSAGE
("Missing: eslint@8.57.1 from lock file"). That broke Render's Docker stage 1
(`RUN npm ci`) and the CI frontend job at its Install step. Missed locally
because an existing `node_modules` hides lock drift — `npm run typecheck` and
`npm run build` pass against stale installs; only a clean `npm ci` catches it.

Fix (c86cd54): regenerated the lock; verified `npm ci` → `typecheck` →
`build` from a clean state locally and in CI (frontend job fully green).

### 2. Latent production bug: missing format-layer deps in the Docker images

Both `deploy/render/Dockerfile` and `backend/Dockerfile` pip-install a
hand-maintained list that never included `python-docx`, `openpyxl`, `xlrd` —
core deps in `pyproject.toml` for the ported DOCX/XLSX/XLS support. The
imports are lazy, so the image booted fine, but every Word/spreadsheet
upload in production would have failed with "Spreadsheet support is not
installed on this server." (Silent feature loss, not a crash — exactly the
kind of thing the never-fabricate rule exists to prevent surfacing
differently.)

Fix (c86cd54): added the three packages to both Dockerfiles.

### 3. Windows footgun caught during local validation: CRLF entrypoint

Built the exact Render image locally to validate the fixes. The container
died instantly with `env: 'bash\r': No such file or directory` (exit 127):
`core.autocrlf=true` checks `entrypoint.sh` out with CRLF on Windows, and
the Docker build copies the working tree, so the shebang reached Linux as
`bash\r`. Committed blobs were already LF (hex-verified), so Render's clone
was unaffected — but anyone building the image on Windows ships a container
that cannot start. (An earlier `git show | Select-String "`r"` check gave a
false negative: PowerShell's pipeline splits on CRLF and strips the CRs
before the pattern sees them — use `git ls-files --eol` instead.)

Fix (92914f0): `.gitattributes` with `*.sh text eol=lf`, which overrides
autocrlf on checkout; working copy refreshed to LF.

### Local end-to-end validation of the Render image

Built `deploy/render/Dockerfile` from the working tree and ran it:
- container reaches **healthy** (Docker HEALTHCHECK on `/health` passes)
- `/health` via nginx → `{"status":"ok","app":"Koverly"}`
- SPA index → 200 text/html; `/api/*` proxied to FastAPI (404 envelope)
- `docx`, `openpyxl`, `xlrd`, `pytesseract`, `pdf2image` importable; Tesseract
  5.5.0 present; `ocr_available()` → True (full OCR stack works in-image)
- nginx tolerates the CRLF working-copy template locally; Render's LF clone
  is unaffected either way

  typecheck + lint + build) both **success**
- 92914f0 pushed after; local image validation above covers what Render

## Session 5 — Move production database to Supabase (efda7d9)

The next deploy log (d8a6f99 build) showed the session-4 diagnostic firing:

    CRITICAL koverly: Startup failed: database unreachable. DATABASE_URL is
    postgresql+asyncpg://koverly:***@dpg-db0moq7avr4c738dveug-a/koverly

`dpg-…-a` is Render's *internal* Postgres hostname, so the web service was
still pointed at the expired Render database. Decision: switch to **Supabase**
instead of recreating a free Render DB that would expire again in ~30 days.

### Changes

1. **`render.yaml`** — removed the `databases:` block and the `fromDatabase`
   wiring; `DATABASE_URL` is now `sync: false` (set once in the dashboard,
   left alone by later Blueprint syncs). Without this, a sync would have
   re-created/re-linked the Render DB and overwritten the Supabase URL.
   Removing a resource from the Blueprint does not delete it on Render — the
   expired database can be deleted manually later.

2. **`app/db/session.py`** — new `build_engine_config()` normalizes the URL
   shapes providers hand you:
   - `postgres://` / `postgresql://` → `postgresql+asyncpg://` (the entrypoint
     does this too; this covers local runs, docker-compose and CI)
   - drops `sslmode`, `pgbouncer`, `connection_limit` — the asyncpg dialect
     forwards *every* URL query parameter to `asyncpg.connect()`
     (`opts.update(url.query)`), which rejects them with `TypeError`
   - transaction-pooler endpoints (port 6543 or `pgbouncer=true`) disable both
     prepared-statement caches: `prepared_statement_cache_size=0` (SQLAlchemy,
     consumed as a DBAPI connect kwarg) and `connect_args={"statement_cache_size": 0}`
     (asyncpg's own cache). Session-pooler and direct connections keep them.
   - SQLite is returned unchanged; the FK-pragma listener now keys off
     `engine.dialect.name` instead of the settings string.
   - SSL needs no configuration: asyncpg defaults to `sslmode=prefer`
     (verified in asyncpg/connect_utils.py, `ssl = 'prefer'` when unset), so
     TLS is negotiated automatically whenever the server offers it — Supabase
     does.

3. **`backend/tests/test_db_config.py`** — 10 tests: both Supabase pooler
   modes, libpq-param stripping, percent-encoded passwords, SQLite
   passthrough, and that the generated kwargs build a real async engine.

4. **Docs** — README "Deploy to Render" rewritten for the Supabase flow;
   `.env.example` documents the session-pooler URI.

### Why the session pooler (port 5432)

- Supabase's direct connection host (`db.<ref>.supabase.co`) is IPv6-only for
  newer projects; Render has no outbound IPv6, so it fails exactly like the
  Render DB did (`socket.gaierror`). The pooler host is IPv4.
- The transaction pooler (6543) also works — the app disables prepared
  statement caching automatically — but session mode behaves like a normal
  Postgres connection and is the default choice for a long-lived server.
- Supabase free projects **pause after ~7 days without activity**; restore
  from the Supabase dashboard if the site has been idle that long.

### Security audit of the exposed `public` schema

Supabase's default ACL grants `anon` / `authenticated` full table privileges
(140 grants each), which would bypass the app's JWT + family scoping if the
Data API were reachable. Checked and mitigated by design:

- RLS is enabled on all 20 tables — Supabase's `ensure_rls` event trigger does
  this automatically for new tables in exposed schemas.
- `pg_policies` is empty: no policy grants access, so `anon` / `authenticated`
  can read and write nothing.
- Tables are owned by `postgres`, the role the app connects as (verified
  `current_user` = `postgres`), so RLS does not interfere with app queries.

No change needed. Note: if supabase-js / the Data API is ever used, this
project would need explicit policies first.
